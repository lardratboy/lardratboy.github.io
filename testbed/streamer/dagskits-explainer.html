DAGs & Kits

The kit world is 65,536 voxels on a side and holds 3.4 trillion solid voxels. It is stored in fewer nodes than a 100×100 thumbnail has pixels, and built in about fifty milliseconds. This page shows why: first the DAG, a tree that never stores the same subtree twice, and then the kit, a way of making content that gives the DAG almost nothing new to store.

01

One node, many places

An octree splits space in half on every axis, again and again, until it reaches single voxels. Stored as a tree, every split costs a node, so a world with a billion voxels of surface costs about a billion nodes. Hash-consing stores the tree differently. A node is its key: its level and the ids of its eight children. Before a node is created, the store looks the key up. If that exact subtree already exists, its id is reused. The tree becomes a directed acyclic graph, where every repeat is a pointer.

The code is three-dimensional, with eight children a node. To make it drawable, the demo below is the same algorithm in two dimensions: a quadtree, four children a node, on a 32×32 grid. Paint on the grid (click and drag). On the right is the store: every unique node, level by level, with the number of places it appears.

Try Sierpiński. Its DAG has exactly one node a level, because each level is three copies of the level below and one empty quadrant. A 65,536³ version would still be one node a level. That is ifsandwhats.md §1's claim, and step 2 measured it on real content: a hash-consed voxel DAG is an iterated function system. Noise is the opposite case. It shares nodes only at the bottom, because a 2×2 block has just 15 non-empty patterns, and above that nothing repeats.

The real store (createStore in dag-core.js) works the same way with 9-word keys, [level, c0 … c7], in an open-addressing table. EMPTY = 0 is shared by every level and never stored. FULL = 1 is a solid voxel only. A solid 16³ block is an ordinary node, one per level, because special-casing it would cost a branch in every walk. Step 2 found that on block-showroom specimens, plain hash-consing is a bottom-of-the-tree effect: 2³ nodes collapse 3,605×, and above 32³ almost nothing repeats (hashcons-findings.md §2). The kit is built so that things repeat at every level.

02

The store only grows

Ids are handed out in creation order, and a node can only be interned once its children exist. So a child's id is always lower than its parent's. dag-core.js relies on that everywhere. createClasses and createCounts make one pass up the ids. census walks them down. prune marks what the roots reach in a single sweep from the top id to the bottom. It needs no stack, because by the time the sweep reaches a node, every node that could keep it has already been seen.

The store is append-only. Every edit you made above interned new nodes, and the old ones stayed behind. Below is every id the demo's store holds, coloured by level. Hollow cells are dead, meaning nothing reachable from the current root points to them. Hover over an id to see its children, which are always to the left. Then prune.

Real builds leave a lot behind. In the lattice at R = 5, the pieces that graft unions were 54–75% of the store. A kit leaves almost nothing: 6,270 interned and 6,261 kept at D = 14, because it is composed directly, with no unions. The prune still matters, because buildKit makes every library entry, and an entry no one picked is dropped. Every chunk worker gets a copy of the store, so dead nodes cost memory several times over.

03

Turned copies

Hash-consing finds identical subtrees. A part that has been turned is not identical. Every node below the turn is new, all the way down to the voxels. The kit turns parts at every level, so in the plain DAG that is where it pays. The cure is to label the edges. Each pointer carries a transform, the store keeps one representative per class (nodes equal up to that transform), and a reader composes the labels as it descends.

Below, sixteen copies of one motif are placed, each turned by a hash. Compare three counts: the plain DAG, classes under the mirrors only (SSVDAG's choice, which is 8 mirrors in 3D and 4 here), and classes under the whole symmetry group (Oh, 48 transforms in 3D; D4, 8 here).

In 3D the kit sketch measured the same effect. With no turns, the D = 12 struct kit is 715 nodes, and with turns it is 6,273, 8.8× as many. Under 48 labels it is 325 classes against 326, so turning every part costs one class. Under SSVDAG's 8 mirrors it is 392 against 1,622, because mirrors can't express a rotation (kit-plan.md §1).

What a label costs is in the reader, not the storage. A 6-bit label fits in the pointer. A traversal keeps a running transform g, one byte, and does two table lookups per step:

// descend through an edge labelled `label` toward the octant you want, o
g      = MUL[g * 48 + label];        // compose: 48×48 table
stored = OCT[INV[g] * 8 + o];        // which stored octant holds it: 48×8 table

Mirrors alone reduce both lookups to XORs, which is why the SSVDAG paper stopped there. The DAG the chunk workers walk is still the plain one. createClasses measures what labels would save, and labels-and-bricks.md sets out the trade.

04

Two binary levels make a 4³ slot grid

A kit assembly is a 4×4×4 grid of slots, and each slot holds a whole entry from the level below. The DAG is binary, so 4³ is two levels of it: eight interns of 2³ slots, then one intern of those eight. There is no graft and no union, only intern. This is the whole of buildKit's composition:

// g[s]: the 64 slot ids, s = x + 4y + 16z.  One level-(k+2) node from them.
for (let O = 0; O < 8; O++){
  for (let o = 0; o < 8; o++) ch[o] = g[(2*(O&1) + (o&1)) + 4*(2*(O>>1&1) + (o>>1&1)) + 16*(2*(O>>2) + (o>>2))];
  top[O] = store.intern(k + 1, ch);
}
return store.intern(k + 2, top);

The 64 slots, as four z-slices · hover a slot

The same slots as two binary levels

The high bit of each coordinate picks the coarse octant O, and the low bit picks the fine one o. Read together, d = 8·O + o is the slot's Morton digit, the same octant-major order the radix-4 port settled on (radix4-addressing.md). That is why a 4³ level costs nothing extra. It was already two binary levels with a convenient name.

05

The library

A kit is nested 4³ assemblies over a small library. Level 0 is a library of 16³ parts: eight structural ones and, by default, four block-showroom specimens as ornaments. Each level above is a library of assemblies. An assembly picks a mask (which of its 64 slots are filled) and, for each filled slot, an entry of the level below and one of the 24 rotations. The top level has one entry, which is the world. Since parts are 2⁴ on a side and each level is two binary levels, D = 4 + 2L.

Which masks an entry may pick depends on its level. That choice is the main control on the look:

The ground is built as nested floors. Half of each level's library (rounded up) is grounded. A grounded entry fills its bottom layer, and each of those 16 slots holds a grounded entry from the level below, turned only about y (Y_TURNS, 4 of the 24). This bottoms out at the block, the slab and the step, all solid for y < 4. So a grounded world is solid in its bottom 4 voxels from edge to edge, and anything that stands on it stands on floors at every scale. The top two levels also place their children upright, so the large structure stands up. Below them, every slot keeps all 24 turns.

The first kitPlan marked a floor slot with s < 16 && y === 0. Since s = x + 4y + 16z, that is the z = 0 row only, so 4 of the 16 bottom slots were floors and the ground had holes. The dense stamp passed, because it stamps whatever the plan says. A separate test of the ground's promise caught it (kit-log.md §2). A stamp checks the composition, not the plan's promises.

06

The kit lab

This lab builds a real kit, in your browser, with the repo's own kitDesc, kitPlan and buildKit. It ray-casts the DAG on the CPU, a port of experiments/kit-sketch.mjs's tracer, and colours each hit with the kit's own kitColour. Every number below the picture is measured on this build, not copied. Drag to look around, scroll to move, and hold shift to move ×8. Hover over the picture to see the voxel's path through the plan, which is the same walk the colour field makes in each chunk worker. Far views sparkle: this is one ray a pixel at full detail, where the viewer would draw coarse lods with averaged colour.

The plan · every entry's mask (underlined: grounded)

The plan is a few typed arrays: per level, per entry, 64 slots of (child index, turn). It is rebuilt from the descriptor in a fraction of a millisecond, so nothing but the descriptor ever needs to be sent anywhere. A chunk worker gets { kind: 'kit', … } and rebuilds the colour field itself. The draws come in a fixed order (the mask, a skyline's heights, then each filled slot's child and turn), so adding one draw anywhere moves every later choice. That is why stream.test.js pins the D = 10 kit to 76,250,785 voxels and 3,092 nodes.

07

What a kit costs

The node count is a library bill. A turned entry is a new node all the way down, but it is hash-consed too: every other copy with the same turn shares all of it. So the store is bounded by roughly 24 × (the parts' nodes + 9 a library entry), whatever D is. Deeper kits add a level of library and almost no nodes. What the measured tables say (kit-findings.md §1):

  • The ground costs nothing. At D = 14 a grounded kit has 6,261 nodes and a floating one 7,110. The upright levels and floors use 4 turns instead of 24, so the grounded kit is smaller, with the same 353 Oh classes, and has more voxels, because floors are solid.
  • Turning costs one class. Under 48 labels a kit is 5–7% of its nodes. Under SSVDAG's 8 mirrors it is 25–26%.
  • Ornaments are the costliest parts. Each specimen brings about 570 nodes with its turns: 3,449 nodes with none, 6,261 with four (45% of the kit), and 12,529 with sixteen.
  • Libraries are the knob that costs, about linearly, and they buy variety, not size:

A cache of copies would not pay. In the street views at D = 14 and 16, only 58–61% of the cut's chunks are distinct (lod, node) pairs, so about 40% are copies. But 94–97% of the chunk jobs' outputs are distinct, because a chunk's records also depend on its neighbours (the apron hides faces, and the seams open where a neighbour isn't drawn), and a kit's copies rarely have the same neighbours. The DAG shares the content. The views of it are still mostly unique.

08

Colour frames, and why far views go grey

The kit's colour is a stand-in you chose: the gamut of a voxel's position in its frame. The frame is the level-colourLevel entry the voxel lies in (level 2 by default, the 256³ buildings), turned with it. A turned copy shows the same colours, turned, so a repeat shows up as a repeated patch of colour. The demo below is a 2D slice of that: a grid of frames, each turned, and next to it what a coarse lod draws, the mean colour of each cell.

Per voxel

Per coarse cell (mean)

When a coarse cell is as large as a frame, the cell averages the frame's whole gamut, and the mean of a gamut is grey. From outside, the D = 14 kit's cut is 17 leaves at lods 6–9, which means cells of 64–512 voxels against 256³ frames. The opening view was confetti at D = 14 and grey at D = 16 (kit-findings.md §2). Nothing is broken. It is what a gamut looks like at a scale coarser than its frame. You picked (c), a two-scale colour: the fine gamut blended with a coarse one, read in level L − 1's frames. It is decided but not built yet. The "two-scale" chip shows roughly what it would do.

A walk through the plan for every point made colour most of a kit job, 30 ms per chunk against 6.4 ms without colour. The fix rests on one fact: level-c entries sit on a world-aligned grid, and a turn about a child's centre maps aligned cells to aligned cells. So each world cell of a frame's side is one affine map, a centre plus a signed permutation, read off four walks and cached. A cache hit costs nine multiply-adds, and since every value is an integer or a half, the cached map gives exactly the walk's answer (kit-log.md §4).

09

How far is endless

A view's cost depends on the view, not the world: 0.3–15M cubes and 1–100 MB at the default detail, whatever the world's size. The kit's node count barely moves with D either (4,935 → 6,261 → 6,990 for D = 12, 14, 16). So the questions about scale are about numbers and engine assumptions, not storage. Slide D.

The next step you asked about is a universe packed full, with caves next to a kit: many DAGs active at once. Today a world is one store, one root and one depth, built whole and copied whole to every worker. universekit.md proposes a universe tree whose top levels are computed from a hash of where they are, never stored, and whose leaves are regions. Each region is a whole world named by a descriptor and built on demand.

The recommended store shape is layers: a shared base, with the parts, the specimens and the IFS materials, plus a tail of new nodes per region. Builds are deterministic, so the main thread and every worker get the same ids from the same name, and no store is shipped. A job says "region kit:4182, lod 3, chunk 5,0,7", and the worker builds the region (about 50 ms for a kit) or takes it from its own cache. That is the kit's "named, not shipped" applied one level up. It is a discussion starter, not a plan. The open questions (which universe, flat or full, how big, gaps between regions, unique or repeated) are listed at the end of docs/universekit.md.
